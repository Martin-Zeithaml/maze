## API ML: z/OSMF `applId` ignored due to case-sensitive variable name

- Issue: [zowe/api-layer#4894](https://github.com/zowe/api-layer/issues/4894)
- Fix: [zowe/api-layer#4903](https://github.com/zowe/api-layer/pull/4903)

### Problem

A customer set a custom z/OSMF application ID in `zowe.yaml`:

```yaml
zOSMF:
  host: example.com
  port: 443
  applId: IZU
```

The start scripts still used the default `IZUDFLT`, so pass ticket generation failed:

```
((o.z.a.p.PassTicketService)) Error during pass ticket generation, userId=MARTIN, applid=IZUDFLT, exception={}
```

### Root cause

- The Zowe launcher exports the YAML key `zOSMF.applId` as `ZWE_zOSMF_applId` (case preserved).
- Both start scripts read `ZWE_zosmf_applId` (lowercase), so the value was never picked up and the `IZUDFLT` default applied.
- Confirmed by a customer workaround that sets the lowercase variable explicitly:

  ```yaml
  zowe:
    environments:
      ZWE_zosmf_applId: IZU  # Force usage of wrong-case variable 
  ```

## Zowe Desktop: user-scope apps missing after login with RBAC

- Issue: [zowe/zlux#1091](https://github.com/zowe/zlux/issues/1091)
- Fix (V3): [zowe/zlux-app-manager#730](https://github.com/zowe/zlux-app-manager/pull/730)
- Fix (V2): [zowe/zlux-app-manager#734](https://github.com/zowe/zlux-app-manager/pull/734)

### Problem

With RBAC enabled (`rbacProfileIdentifier` set in `zowe.yaml`), an app defined only in a user's `allowedPlugins.json` does not appear in the Desktop launchbar after an interactive login:

```
$ZWE_zowe_workspaceDirectory/app-server/ZLUX/pluginStorage/org.zowe.zlux.bootstrap/plugins/users/<USERNAME>/allowedPlugins.json
```

- Reproduced by logging in from a new incognito window; the app is missing.
- Pressing F5 makes it appear.
- Server-side RBAC filtering works correctly, so the bug is client-only.

### Root cause

- The Desktop calls `GET /plugins?type=all` once at page load, before authentication, so the response has no user-scope apps.
- After login, `performPostLoginActions` in `authentication-manager.service.ts` calls `loadApplicationPluginDefinitions()` without the `update` flag.
- Because the plugin definitions from the pre-login load are already cached, `PluginManager` returns them and never re-fetches with the authenticated session.
- F5 fixes it because the reloaded page sends the session cookie on that first request.

## Checking the installed component version in a corrupted installation

### Problem

Zowe is failing before any API ML components can start, and we suspect the installation may be corrupted. We need to verify which version is currently installed.

### Reading the manifest with `jar`

Example for the gateway:

```sh
cd /zowe/components/gateway
jar -xf gateway-service-lite.jar META-INF/MANIFEST.MF
chtag -tc ISO8859-1 ./META-INF/MANIFEST.MF
cat ./META-INF/MANIFEST.MF
```

### Alternative: `unzip`

```sh
unzip -p gateway-service-lite.jar META-INF/MANIFEST.MF | iconv -f ISO8859-1 -t IBM-1047
```

### Note

Both approaches are only an idea of where the version is defined, and neither is guaranteed to work on every system:

- `jar` extracts the manifest to disk, so it might fail on a read-only filesystem, which is the recommended setup.
- `unzip` might not be present on the system.
